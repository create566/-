📌 第三层：AlertPipeline 告警管道（核心调度）

路径：alert/pipeline.py 的 run() 方法，8 个步骤串起来

  1. 冷却检查 — 60 秒内同一个系统不重复告警，防止刷屏
  2. 加载历史 — 从 store 取最近 60 条检测记录，给 Agent 做趋势分析用
  3. 调用 Agent — agent_graph.ainvoke({...}) 启动 Plan→Execute→Replan 三步
  4. 保存检测历史 — 无论正常还是异常，每次检测结果都存下来
  5. 判断结果 — normal 就健康分 +5 结束；warning/critical 继续下面步骤
  6. 飞书推送 — 拼 Markdown 卡片（异常表格 + 诊断摘要）→ POST 到飞书 Webhook
  7. 扣健康分 — critical 扣 20、warning 扣 10
  8. 存故障记录 — 故障详情存 incidents.json/MySQL，报告存 reports/ 目录
📌 第四层：8 个检测器怎么工作

🏠 本地检测器（不需要外部服务）

  1. local_cpu → psutil.cpu_percent(interval=1)
  2. local_memory → psutil.virtual_memory().percent
  3. local_disk → shutil.disk_usage(path)
  4. http_health → httpx.get(url/health)

☁️ 远程检测器（需要连接外部服务）

  1. prometheus_cpu → PromQL 查 node_cpu
  2. prometheus_memory → PromQL 查 node_memory
  3. mysql_slow_queries → SHOW GLOBAL STATUS LIKE 'Slow_queries'
  4. redis_memory → r.info("memory")

🔌 检测器是怎么注册的？

  1. 每个检测器类上面有 @register_detector("local_cpu") 装饰器
  2. Python 在 import app.detectors.local 时自动执行装饰器，把类存到 DetectorRegistry 字典里
  3. Executor 执行时调用 DetectorRegistry.get_or_create("local_cpu") 拿到实例
📌 第五层：知识库 RAG（AI 诊断时怎么查资料）

三层降级：先向量搜 → 不行就关键词匹配 → 再不行就空

  1. 首选：Milvus 向量检索 — 把异常描述（如"CPU 85% 使用率过高"）转成 1024 维向量 → 在知识库里找最相似的 5 个段落
  2. 降级：TAG_INDEX 关键词 — Milvus 挂了就用字典匹配，比如"cpu"关键词 → cpu_high_usage.md
  3. 兜底：返回空 — 告诉 LLM "暂无知识库参考"，LLM 凭自己的知识写报告

📚 知识库里有什么？7 篇运维文档

cpu_high_usage.md        → CPU 飙高怎么处理（死循环/流量突增/定时任务重叠/慢查询）
memory_high_usage.md     → 内存泄漏怎么排查
disk_high_usage.md       → 磁盘满了怎么办
mysql_slow_query.md      → 慢查询怎么优化
redis_memory_high.md     → Redis 内存高了怎么处理
service_unavailable.md   → 服务挂了怎么恢复
slow_response.md         → 响应慢怎么诊断

每篇文档按 ## 二级标题切成多个段落，每个段落标记类型：问题描述/排查步骤/根因分析/处理方案/紧急处理/验证步骤。
索引入 Milvus 时：段落内容 → Embedding 模型 → 向量 → 存入。检索时：问题 → 向量化 → 搜相似段落。

📌 第六层：飞书双通道

📤 通道① Webhook（自动推）

  1. AlertPipeline 检测到异常
  2. 调用 FeishuNotifier.send_markdown()
  3. POST 飞书 Webhook URL
  4. 群聊收到 Markdown 卡片

代码：tools/feishu_notifier.py

📥 通道② WebSocket（你主动问）

  1. 独立进程 run_feishu_ws.py 保持长连接
  2. 你在群里 @机器人 "状态"
  3. WS 收到消息 → POST /api/feishu/handle
  4. 主服务解析命令 → 返回结果

代码：run_feishu_ws.py + api/monitoring.py:251

📌 第七层：数据存储（自动降级）

存哪里？MySQL → 连不上就 JSON 文件

dao/store.py 里每个函数都是这样的结构：

def get_system(id):
    if _engine is None:           ← MySQL 连不上
        return 从 JSON 文件读       ← data/systems.json
    else:                         ← MySQL 正常
        return 从 MySQL 查         ← systems 表

三张表 = 三个 JSON 文件：
systems 表 → data/systems.json（系统配置）
incidents 表 → data/incidents.json（故障记录）
check_history 表 → data/check_history.json（每次检测的指标值）

📌 总结：一条请求的完整路径
定时器响 ──→ AlertPipeline.run()
                │
                ├── 1. 冷却检查（60s 不重复）
                ├── 2. 加载历史（60条）
                ├── 3. Agent.ainvoke()
                │       ├── Planner:  排顺序 [CPU→内存→磁盘]
                │       ├── Executor: 一个个调检测器取数据（循环）
                │       └── Replanner: 毛刺过滤→RAG查知识库→LLM写报告
                │
                ├── 4. 保存检测历史
                │
                └── 5. 结果
                     ├── normal → 健康+5 → END
                     └── anomaly → 飞书推送 → 扣分 → 存故障 → END
